# Hangulpia 변환 엔진 가이드

한글(두벌식) → 일본어(히라가나) 변환 "모델"이 실제로 무엇이고, 어떻게 만들어지고,
어디서 어떻게 구동되는지 정리한 문서입니다. 딥러닝 모델이 아니라 **통계적 음소 정렬
테이블(PhoneticMap) + 손으로 정리한 문법 예외 규칙**으로 이루어져 있습니다.

- 코드 위치: `core/crates/db/src/phonetic_decoder.rs` (핵심 엔진, 유일한 정답 소스)
- 관련 데이터: `core/crates/db/src/vocab.rs`, `vocab_extended.rs`, `vocab_gapfill.rs`
  (`vocab_large.rs`는 파일만 남아있고 **더 이상 안 씀** — 1.4절 참고)
- 실사용처: macOS 앱(`core/crates/macos-ime`, C FFI), 홈페이지 데모(`core/crates/wasm` → WASM,
  **JS 손포팅 아님** — 2026-07-25부터 같은 Rust 코드가 인터페이스만 바꿔 두 곳 다 돌아감)

## 1. 모델(PhoneticMap)을 생성하는 방법

### 1.1 이게 "학습된 모델"이 아닌 이유

이름은 통계적이지만 신경망 학습이 아닙니다. **결정론적으로 계산 가능한 역방향
테이블**을 만드는 것에 가깝습니다.

- 일본어 히라가나 → 한글 표기는 규칙만으로 결정됩니다 (`kana_hangul.rs`의
  `hiragana_to_hangul()` — つ→츠, ち→치 같은 고정 매핑).
- 그래서 (히라가나 읽기, 한글 표기) 쌍이 있으면, 그 반대 방향(한글→히라가나)의
  빈도 기반 확률 테이블을 **역산**할 수 있습니다. 이게 `PhoneticMap`입니다.

`align_hiragana_hangul()`은 ん(받침 처리)/っ(촉음)/요음(2글자 히라가나 ↔ 1글자
한글) 같은 비1:1 매칭까지 처리합니다.

#### 1.4.1 `vocab_jlpt.rs` 출처와 처리 방법 (v0.1.8)

- **원본**: [`elzup/jlpt-word-list`](https://github.com/elzup/jlpt-word-list) (MIT
  라이선스) — `tanos.co.uk`에서 정리된 JLPT 어휘를
  `jamsinclair/open-anki-jlpt-decks` Anki 덱으로, 다시 CSV로 옮긴 공개
  데이터. N5(717행)/N4(667행)/N3(2,139행) 세 파일을 사용.
- **처리 파이프라인** (기계적 변환, 손으로 재입력 안 함 — 오타/환각 위험을
  원천 차단):
  1. 기존 3개 파일(`vocab.rs`+`vocab_extended.rs`+`vocab_gapfill.rs`)에서
     정규식으로 (표기, 읽기) 쌍을 전부 추출해 중복 제거용 집합을 만듦.
  2. CSV에서 `～구` 같은 접사/조수사 항목(독립된 단어로 못 씀)과 가타카나
     읽기 항목(엔진이 히라가나만 생성하므로 절대 매칭될 일이 없어 죽은
     항목이 됨)을 제외.
  3. `"足; 脚"` / `"行く"`+`"いく; ゆく"` 같은 이표기·이표음 항목은
     표기·읽기 개수에 맞춰 각각의 조합으로 분리.
  4. 위 1의 기존 집합 및 N5→N4→N3 순서로 레벨 간 중복도 제거.
  5. 남은 항목만 `VocabEntry::new(surface, reading, pos, category)`로
     변환해 `vocab_jlpt.rs`에 씀. `pos`는 영문 뜻이 "to "로 시작하면
     Verb, 표기·읽기가 둘 다 い로 끝나면 IAdjective, 나머지는 Noun으로
     휴리스틱 분류 — `pos`/`category`는 `generator.rs`(연구용 합성
     코퍼스 생성기)에서만 쓰이고 실제 앱/홈페이지 변환 경로에는 전혀
     영향을 주지 않으므로(2.1절 무엇이 겹치고 안 겹치는가 참고)
     분류가 다소 부정확해도 실사용 정확도에는 무해함.
  6. 결과: N5 290개 + N4 392개 + N3 1,750개 = 신규 **2,432개**.
- **검증**: 표본 스팟체크(중복 0건, 내부 중복 0건, 비-히라가나 읽기 0건
  자동 검사) + `ime-db` 회귀 테스트
  (`test_jlpt_vocab_words_decode_correctly`)로 신규 단어 3개가 실제
  `PhoneticMap`을 통해 올바르게 디코딩되는지 확인.
- **주의**: 이 확장은 `vocab_large.rs`와 달리 카테시안 곱으로 조합 생성한
  게 아니라, 실존하는 공개 어휘 목록을 그대로 옮긴 것이라 1.4절 초반에
  설명한 "가짜 단어" 문제와는 다른 종류입니다. 다만 이 과정에서 별개의
  **기존 버그**(촉음 っ 학습 정렬 문제)를 발견했습니다 — 4.5절 참고.

`vocab_large.rs`(22,741개)는 파일은 남아있지만 **더 이상 어디서도 안 씁니다**
(1.4절 함정 문단 아래에서 이유 설명).

### 1.5 예외 규칙 (통계로 안 잡히는 것들)

`PhoneticMap`은 문자 정렬 통계라서 **문법**을 모릅니다. 조사 は(발음 wa)나
です/ます 활용형처럼 "문맥에 따라 다르게 써야 하는" 패턴은 학습으로 안 풀려서,
`phonetic_decoder.rs`에 하드코딩된 예외 테이블로 별도 처리합니다:

```rust
const KNOWN_WORDS: &[(&str, &str)] = &[
    ("사쿠라", "さくら"), ("아리가토", "ありがとう"), ("곤니찌와", "こんにちわ"),
    /* ... */
];

const KNOWN_SUFFIXES: &[(&str, &str)] = &[
    ("데스카", "ですか"), ("데스", "です"), ("마스", "ます"),
    ("와", "は"), // 조사, 반드시 맨 뒤(최단 매치)에 위치
];
```

새 예외를 추가하고 싶으면 이 두 배열에 추가하면 끝입니다. ~~JS 쪽에도 손으로
동기화~~ — 2026-07-25 WASM 전환 이후로는 필요 없습니다. 홈페이지가 이 Rust
코드를 컴파일한 걸 그대로 쓰기 때문에, `wasm-pack` 재빌드(3.4절)만 하면
자동으로 반영됩니다.

### 1.6 사용자 마커 (`~` 장음 / `^` 탁음, v0.1.7)

예외 테이블로도 못 잡는 경우(사전에 없는 단어, 표기가 애매한 고유명사 등)를
위해 사용자가 변환 결과를 직접 지정할 수 있는 마커 두 개를 추가했습니다.
음절(한글 한 글자) 바로 뒤에 붙입니다:

| 마커 | 효과 | 예시 |
|---|---|---|
| `~` | 해당 음절의 모음을 장음으로 연장 | `도~` → `どう` |
| `^` | 해당 음절을 탁음으로 전환 | `카^` → `が` |
| 조합 | 같은 음절에 둘 다 적용 가능 | `카^~` → `があ` |

구현은 `phonetic_decoder.rs`에 있고, `decode_word()`가 단어에 `~`나 `^`가
섞여 있으면 곧바로 별도 경로(`decode_word_with_markers`)로 분기합니다:

```rust
fn decode_word(&self, word: &str, kanji: Option<&HashMap<String, String>>) -> String {
    if word.contains('~') || word.contains('^') {
        return decode_word_with_markers(self.map, word);
    }
    // ... 기존 KNOWN_WORDS / KNOWN_SUFFIXES / decode() 경로
}
```

`decode_word_with_markers`는 마커가 붙은 음절만 처리하고, 자음 기본값은
`base_reading_for_marker()`를 통해 **학습된 `PhoneticMap`을 먼저 조회**한
뒤(없으면 정적 폴백) 결정합니다 — 이렇게 해야 같은 글자를 마커 없이 변환한
결과와 자음이 어긋나지 않습니다(예: 마커 없는 "도"가 이미 `ど`로 나온다면,
"도~"도 `どう`여야지 `とう`가 되면 안 됨). `apply_dakuten()`은 か/さ/た/は
행의 어두 자음을 탁음으로 바꾸는 조회 테이블이고, `long_vowel_extension()`은
마지막 히라가나 문자의 모음(a/i/u/e/o)에 맞는 연장 문자를 고릅니다
(a→あ, i→い, u→う, e→い, o→う).

**왜 이번엔 안전한가** — 연구 논문(5장, 4.10절 "장음 마커 분석")은 정확히
같은 아이디어(틸드 마커)를 시도했다가 정확도가 -22.3%p 떨어졌다고
보고합니다. 다른 실패가 아니라 **다른 위치에 적용했기 때문**입니다. 논문
쪽은 `~`를 `PhoneticMap`을 학습시키는 코퍼스/입력 스트림에 섞어 넣어서
통계 모델 전체의 정렬을 어긋나게 만들었습니다. 이번 구현은 마커가 붙은
음절 하나만 국소적으로 별도 처리하고 문장의 나머지는 기존 통계 경로를
그대로 타므로, 마커가 없는 텍스트의 정확도에는 전혀 영향이 없습니다.
자세한 비교는 6절 연결 노트를 참고하세요.

macOS 앱에서 `~`/`^`가 실제로 엔진까지 도달하려면 Swift 쪽 라우팅도
필요합니다 — `HJInputController.swift`의 `handle()`이 조합 중(mid-composition)
이 두 문자를 `handleJamo()` 경로로 넘기도록 분기를 추가해뒀습니다(안 그러면
바로 커밋되어 `hangulBuffer`/Rust 엔진에 닿지 못함). 홈페이지 사용법 안내는
`#tutorial` 섹션(TRACK 05)에 있습니다.

## 2. 모델을 이용하는 방법 (Rust API)

### 2.1 최소 예시

```rust
use ime_db::phonetic_decoder::{PhoneticMap, BeamDecoder};
use ime_db::kana_hangul::hiragana_to_hangul;
use ime_db::vocab::build_vocab;
use ime_db::vocab_extended::build_extended_vocab;
use ime_db::vocab_gapfill::build_gapfill_vocab;

let mut vocab = build_vocab();
vocab.extend(build_extended_vocab());
vocab.extend(build_gapfill_vocab());

let pairs: Vec<(String, String, u64)> = vocab.iter()
    .map(|v| (v.reading.to_string(), hiragana_to_hangul(v.reading), 100u64))
    .collect();

let mut map = PhoneticMap::new();
map.build_from_pairs(&pairs);

let decoder = BeamDecoder::new(&map, /* beam_width */ 6, /* max_candidates */ 5);

// 추천 API — 문장 단위, 예외 규칙 자동 적용, 최선 후보 1개만 반환
let result: String = decoder.decode_sentence("나마에와 난데스카");
// => "なまえは なんですか"

// 원시 API — 후보 여러 개 + 신뢰도 (단어 하나 단위, 예외 규칙 미적용)
let candidates: Vec<(String, f64)> = decoder.decode("사쿠라");
// => [("さくら", 0.97..), ...]
```

`decode_sentence()`가 실제 앱과 동일한 결과를 주는 진입점입니다.
`decode()`를 직접 쓸 거면 조사/활용형 예외가 안 걸린다는 점을 기억하세요.

## 3. 웹페이지에서 모델을 이용하는 방법 (구동·연동 메커니즘)

### 3.1 요약 (2026-07-25부터: WASM, 더 이상 JS 손포팅 아님)

**처음엔 `phonetic_decoder.rs`의 로직을 JavaScript로 손으로 옮겨서 썼습니다.**
문제는 손포팅이 구조적으로 계속 어긋난다는 것 — 실제 앱은 학습된
통계 맵(`PhoneticMap`)을 쓰는데 JS 버전은 그게 없어서, 예를 들어 `나니오
타베마스카`가 실제 앱에서는 `なにお たべますか`(정답)로, JS 데모에서는 `なにお
たへますか`(오답)로 서로 다르게 나오는 게 실측으로 확인됐습니다.

그래서 **로직을 다시 옮기는 대신, 같은 Rust 엔진을 WebAssembly로 컴파일해서
브라우저에서 그대로 돌리는 방식으로 바꿨습니다.** `crates/wasm`이 `hj_engine_init()`
(macOS 앱)과 **완전히 동일한 어휘 4종 조합**으로 `PhoneticMap`을 만들고,
`BeamDecoder::decode_sentence_with_kanji()`를 `wasm-bindgen`으로 노출합니다.
인터페이스(FFI vs. WASM)만 다르고 모델은 100% 같은 코드입니다.

```
core/crates/db/src/phonetic_decoder.rs   (Rust, 유일한 정답 소스)
        │
        ├─▶ crates/macos-ime (C FFI)   ──▶ 다운로드 앱
        └─▶ crates/wasm (wasm-bindgen) ──▶ homepage/wasm/*.wasm ──▶ 브라우저
```

### 3.2 `crates/wasm` 구조

- `rusqlite`는 `wasm32-unknown-unknown` 타겟을 지원하지 않아서, `ime-db`에
  `sqlite` feature를 새로 만들고(`crates/db/Cargo.toml`) SQL 의존 모듈
  (`dictionary`/`embedding`/`sentence`/`trainer`/`ngram`/`autocomplete`,
  `DictionaryDb`)을 `#[cfg(feature = "sqlite")]`로 감쌌습니다. `phonetic_decoder`/
  `vocab*`/`kana_hangul`/`corpus`/`generator`는 원래도 순수 Rust라 항상 컴파일됩니다.
  macOS 앱/CLI는 기본 feature(`sqlite` 켜짐) 그대로 빌드되어 영향 없습니다.
- `crates/wasm/src/lib.rs`가 노출하는 함수 3개:
  - `convert(input) -> String` — 한자 치환 포함 (홈페이지 연습장이 씀)
  - `convert_hiragana_only(input) -> String` — 히라가나만, 실제 앱의 실시간
    조합 텍스트(`hj_hangul_to_hiragana`)와 동일 (지금은 미사용, 필요시 활용 가능)
  - `vocab_size() -> usize` — 학습된 고유 한글 토큰 수
- 칸지 사전은 SQL `KanjiDict` 대신 그냥 `HashMap<String,String>`으로, **macOS
  앱과 완전히 동일한 어휘 조합**으로 만듭니다. 처음엔 `vocab_large.rs`도
  포함해서 만들었는데, 그러면 그 데이터 품질 문제(6.3절)가 웹 데모와 앱
  양쪽에 똑같이 나타난다는 게 오히려 장점이라 판단했었습니다 — 한쪽만
  몰래 고쳐진 상태로 남지 않으니까요. 실제로 v0.1.6에서 `vocab_large.rs`를
  양쪽에서 동시에 제거하면서 그 설계가 그대로 들어맞았습니다.
- `decode_sentence()`(기존, 앱이 씀)와 `decode_sentence_with_kanji()`(신규,
  WASM이 씀)는 `phonetic_decoder.rs` 안에서 로직을 공유합니다 — 칸지 사전이
  없으면(`None`) 예전과 100% 동일하게 동작.

### 3.3 어떻게 개발했는가 (진행 순서 그대로)

나중에 비슷한 걸 또 만들거나 이걸 고쳐야 할 때 참고할 수 있도록, 실제로 밟은
순서를 기록합니다.

1. **문제 재현부터** — "홈페이지 연습기랑 실제 다운로드 앱이랑 성능이 같냐"는
   질문에 감으로 답하지 않고, 실제 Rust 엔진과 JS 데모에 같은 문장을 넣어
   직접 대조했습니다(`나니오 타베마스카` → 실제 앱은 `たべますか` 정답, JS
   데모는 `たへますか` 오답). 이 비교 결과가 "손포팅은 구조적으로 못 고친다"는
   결론과 WASM으로 가는 근거가 됐습니다.
2. **인터페이스 방식 결정** — WASM vs. Lambda API 서버 두 가지를 검토. 이
   프로젝트가 처음부터 "정적 사이트, 서버 없음, $0"을 지켜온 걸 감안해서
   WASM으로 결정(2절 "구현 방식" 질문에서 사용자가 직접 선택).
3. **컴파일 장애물 확인** — `ime-db`를 그냥 wasm32 타겟으로 빌드해보니
   `rusqlite`(SQLite를 C로 번들링) 때문에 실패할 게 뻔했음. 실제로 필요한 건
   `phonetic_decoder`/`vocab*`/`kana_hangul`뿐이고 SQL 기반 모듈
   (`dictionary`/`embedding`/`sentence`/`trainer`/`ngram`/`autocomplete`)은
   전혀 안 씀 → `rusqlite`를 `sqlite` feature 뒤로 숨기는 걸로 해결
   (`crates/db/Cargo.toml`, `lib.rs`에 `#[cfg(feature = "sqlite")]` 도배).
   `cargo build -p ime-db --no-default-features`로 sqlite 없이도 빌드되는지
   먼저 확인하고, `cargo test -p ime-db`(기본 feature, sqlite 켜짐)로 기존
   111개 테스트가 안 깨지는지 확인한 다음에야 다음 단계로 넘어갔습니다.
4. **칸지 사전 설계 — SQL 없이** — 기존 macOS 앱은 `KanjiDict`(SQLite 테이블)로
   칸지를 찾는데, wasm에선 SQL을 뺐으니 그대로 못 씁니다. 대신 어휘
   목록(`reading`, `surface`)을 그냥 `HashMap<String,String>`으로 한 번 만들어
   메모리에 올려두는 방식으로 대체 — 코드 몇 줄로 끝났고, macOS 앱과 완전히
   같은 어휘(`vocab_large.rs` 포함)를 쓰기로 했습니다(6.3절 데이터 품질 이슈도
   그래서 "둘 다 똑같이 걸리고, 고치면 둘 다 한 번에 고쳐지는" 상태로 정리).
5. **`decode_sentence` 리팩터링** — 기존 `decode_sentence()`(앱이 씀, 칸지 없음)를
   건드리지 않으면서 칸지 버전을 추가해야 했음. 문장을 단어로 쪼개는 루프를
   `decode_sentence_inner(hangul, kanji: Option<&HashMap<...>>)`로 한 번만 두고,
   `decode_sentence()`는 `None`을 넘기고 `decode_sentence_with_kanji()`는
   `Some(...)`을 넘기는 얇은 wrapper 두 개로 분리 — 로직 중복 없이 두 API를
   같은 함수에서 파생시켰습니다. 리팩터링 직후 `cargo test -p ime-db
   phonetic_decoder`로 기존 11개 테스트가 그대로 통과하는지 재확인.
6. **네이티브 빌드로 먼저 검증, 그다음 wasm32** — `cargo build -p ime-wasm`
   (호스트 macOS 타겟)으로 크레이트 자체의 타입/로직 오류를 먼저 잡고 나서
   `wasm-pack build`(wasm32 타겟)로 넘어갔습니다 — wasm 타겟은 빌드가 느리고
   에러 메시지도 덜 친절해서, 순수 Rust 오류는 네이티브에서 먼저 걸러내는 게
   빠릅니다.
7. **실제 결과 대조로 검증** — `wasm-pack` 산출물을 Node.js로 직접 로드해서
   (`import init, { convert } from './ime_wasm.js'` + `init({ module_or_path:
   <파일 버퍼> })`) 실제 Rust `BeamDecoder`로 이미 확인해둔 문장들을 다시
   돌려서 **한 글자도 안 틀리고 일치**하는지 확인. 배포 후에도
   `https://hangulpia.com/wasm/ime_wasm.js`를 그대로 fetch해서 같은 방식으로
   라이브 검증까지 했습니다 — "배포됐다"와 "배포된 게 맞게 동작한다"는
   다른 확인이라는 원칙.
8. **낡은 코드 제거** — 새 걸 넣고 옛날 걸 남겨두면 또 헷갈리므로, 손포팅
   JS 엔진 전체(~240줄)와 `kanji-dict.js`를 완전히 삭제하고, `grep`으로
   `hangulToHiragana`/`convertWord`/`KANJI_DICT` 등 잔재가 없는지 확인했습니다.
9. **(이어서, 같은 날) `vocab_large.rs` 제거** — WASM으로 통합하고 나니
   "실제 앱도 vocab_large 재필터링할까?"라는 질문이 자연스럽게 나왔고,
   `HashMap` 통계로 어간·어미 조합 개수를 세어(3.2절) 22,741개 중 81%가
   기계 생성 비단어라는 걸 수치로 확인한 뒤 macOS 앱(`ffi.rs`)과
   `crates/wasm` 양쪽에서 동시에 뺐습니다 — WASM으로 통합해둔 덕분에
   "양쪽 다 고쳐야 하나?"라는 질문 자체가 "한 군데만 고치면 끝"으로
   바뀐 첫 실제 사례입니다. 1.4절에 상세 기록.

### 3.4 어떻게 쓰는가 (개발자용)

**어휘를 고친 뒤 재빌드:**
```bash
cd core/crates/wasm
wasm-pack build --target web --release --out-dir ../../../homepage/wasm
```
- 산출물(`homepage/wasm/ime_wasm_bg.wasm` 약 956KB, gzip 약 310KB)은 **git에
  커밋**합니다 — macOS 앱 zip과 같은 방식으로, CI에는 Rust/wasm-pack 빌드
  스텝이 없습니다(3.5절 배포 메커니즘 그대로).
- `wasm-pack`이 기본으로 `homepage/wasm/.gitignore`(내용 `*`)를 새로 만드는데,
  이러면 다음 빌드부터 산출물이 git에서 계속 빠지니 **매번 지워야 합니다**
  (`rm homepage/wasm/.gitignore`).
- 필요 도구: `rustup target add wasm32-unknown-unknown`, `cargo install
  wasm-pack` (둘 다 이미 이 환경에 설치돼 있었음).

**로컬(브라우저 없이 Node.js)에서 바로 테스트:**
```bash
cd homepage/wasm
node --input-type=module -e "
import init, { convert, convert_hiragana_only, vocab_size } from './ime_wasm.js';
import { readFile } from 'node:fs/promises';
await init({ module_or_path: await readFile('./ime_wasm_bg.wasm') });
console.log('vocab_size:', vocab_size());
console.log(convert('나마에와 난데스카'));
"
```

**브라우저(홈페이지)에서 쓰는 법** — `homepage/index.html` 맨 아래
`<script type="module">`가 이미 이렇게 붙어 있습니다:
```html
<script type="module">
  import init, { convert } from './wasm/ime_wasm.js';
  await init();                    // .wasm fetch + 인스턴스화, 페이지당 한 번만
  var result = convert('한글 문장'); // 이후로는 동기 호출, 네트워크 왕복 없음
</script>
```
`convert()` 외에 `convert_hiragana_only()`(칸지 없이 히라가나만, 실제 앱의
`hj_hangul_to_hiragana`와 동일 동작)와 `vocab_size()`도 같은 방식으로 가져다
쓸 수 있습니다 — 지금은 `convert()`만 페이지에서 쓰고 있습니다.

**Rust 엔진 자체를 고칠 때**(예: `KNOWN_SUFFIXES`에 새 조사 추가) — 이제
`homepage/index.html`은 건드릴 필요가 **없습니다.** `phonetic_decoder.rs` 고치고
→ `cargo test -p ime-db phonetic_decoder`로 회귀 확인 → 위 wasm-pack 명령
재실행 → 커밋. 예전처럼 JS 쪽을 손으로 동기화하는 단계 자체가 사라졌습니다
(1.5절의 "반드시 양쪽 다 수정" 경고는 이제 macOS 앱 vs. 홈페이지가 아니라,
`decode_sentence()`를 쓰는 곳 전체에 자동으로 적용됨).

## 4. 다운로드해서 이용하는 방법 및 구동 메커니즘 (macOS 앱)

### 4.1 사용자 입장에서

```bash
# hangulpia.com에서 HangulJapaneseIME-latest.zip 다운로드 후
unzip HangulJapaneseIME-latest.zip
cd HangulJapaneseIME-v0.1.3-arm64
bash install.sh
# 로그아웃 → 재로그인
# 시스템 설정 → 키보드 → 입력 소스 편집 → + → 일본어 카테고리 → 한글일본어입력기
```

- 요구사항: macOS 13+ (Ventura), Apple Silicon(arm64) 전용 — Intel Mac/Windows 미지원
  (Windows 소스는 `core/crates/windows-ime`에 있지만 빌드된 배포판 없음)
- 제거: `bash uninstall.sh`

### 4.2 아키텍처

```
┌─────────────────────────────────────────┐
│  Swift (InputMethodKit 앱)                │
│  HJInputController.swift  ← 키 입력 수신   │
│  HJEngine.swift           ← FFI 래퍼      │
└───────────────┬───────────────────────────┘
                │ C FFI (extern "C")
                ▼
┌─────────────────────────────────────────┐
│  Rust (libhj_engine.a, 정적 라이브러리)    │
│  crates/macos-ime/src/ffi.rs              │
│    hj_engine_init()                       │
│    hj_hangul_to_hiragana()  ← 실시간 조합용│
│    hj_convert()             ← 후보창용     │
└─────────────────────────────────────────┘
```

### 4.3 구동 메커니즘 (런타임)

1. **앱 시작 시** (`HJEngine.shared.initialize()` → `hj_engine_init()`):
   - 4,153개 전체 어휘(1.4절)로 `PhoneticMap`을 **매번 새로 빌드** (파일 저장/로드 없음, 순수 in-memory)
   - 칸지 사전도 같은 어휘로 in-memory SQLite(`:memory:`)에 적재
2. **타이핑 중** (실시간 조합 텍스트):
   - `HJInputController`가 두벌식 자모를 `hangulBuffer`에 누적
   - 매 키 입력마다 `HJEngine.shared.toHiragana()` → `hj_hangul_to_hiragana()`
     → `BeamDecoder::decode_sentence()` (v0.1.3부터 조사/활용형 예외 규칙 포함)
   - 결과를 조합 중 텍스트로 화면에 표시
3. **후보 선택** (숫자 1-9로 대체 후보 고를 때):
   - `HJEngine.shared.convert()` → `hj_convert()` → `BeamDecoder::decode()`로
     후보 여러 개 생성 → 각 후보로 칸지 사전 조회 → 점수순 정렬해 후보창에 표시
4. **확정** (스페이스/엔터): 조합 중이던 히라가나(또는 선택한 칸지 후보)가 커밋됨

### 4.4 빌드 메커니즘 (개발자용)

```bash
cd core/crates/macos-ime
./build.sh build      # 빌드만
```

### 한글→일본어 입력기 엔진: 다단계 음소-의미 변환 파이프라인 설계 및 실험

#### 초록

본 논문은 한글 키보드 배치를 활용하여 일본어 텍스트를 입력할 수 있는 새로운
입력기 엔진(IME)의 설계, 구현, 그리고 포괄적인 실험 평가를 제시한다. 본
시스템은 한글 음소 표현을 정확한 일본어 텍스트(히라가나, 가타카나, 한자)로
변환하는 고유한 크로스 링귀스틱 과제를 해결한다. 음소 임베딩 기반 디코딩,
인접문장 공출현 임베딩, N-gram 언어 모델, 4요소 가중 랭킹 공식을 결합한
다단계 파이프라인을 통해, 14개의 체계적 실험을 수행하여 Top-1 표기 정확도
62.1%, 키 입력 효율(KSPC) 0.85를 달성하였다. 이는 표준 로마지 입력(KSPC 2.0)
대비 57.5% 효율적이다. macOS(InputMethodKit) 및 Windows(키보드 훅) 네이티브
앱으로 배포하여 실용성을 입증하였다.

#### 1. 서론

일본어 텍스트 입력 시스템은 광범위한 연구와 상업적 개발의 대상이 되어왔다.
지배적인 방식인 로마지 입력은 사용자가 일본어 발음의 로마자 표현을
입력하면(예: "arigatou" → ありがとう) 히라가나로 변환한 후 사전 검색과 언어
모델링을 통해 한자로 변환하는 방식이다. 본 논문은 대안적 접근법으로 한글
키보드 배치를 일본어 음소 입력 매체로 활용하는 방법을 탐구한다.

한글은 일본어 음소 입력에 독특한 이점을 제공한다. 한글은 초성-중성-종성
음소를 하나의 콤팩트한 음절 블록으로 인코딩하는 자질 문자(featural
alphabet)이다. 하나의 한글 음절 블록은 일본어 모라(mora) 하나를 1~2번의 키
입력으로 표현할 수 있어, 로마지의 2~4번과 비교하면 효율적이다. 예를 들어,
일본어 か(ka)는 로마지로 k+a 2키가 필요하지만, 한글 두벌식 배치에서는
ᄏ+ᅡ로 동일하게 2키이면서도 더 복잡한 음절에서는 큰 차이를 보인다.

**1.1 문제 정의**

한글→일본어 변환 파이프라인은 표준 일본어 IME와 구별되는 여러 기술적 과제에
직면한다. 첫째, 한국어와 일본어 간의 음소 매핑이 본질적으로 모호하다: 여러
히라가나 시퀀스가 동일한 한글 표현을 생성할 수 있다(예: つ(tsu)와
ちゅ(chyu)가 유사한 한글로 매핑). 둘째, 일본어 장음(예: こう kou vs. こお
koo)이 한글 영역에서 추가적인 모호성을 생성한다. 셋째, 히라가나 후보 자체가
확률적이므로 기존 IME보다 훨씬 더 큰 후보 공간에서 한자 판별을 수행해야 한다.

**1.2 기여**

본 논문의 기여는 다음과 같다: (1) 한글 입력에서 히라가나 Top-1 정확도
90.5%를 달성한 음소 임베딩 모델(규칙 기반 대비 +30.9%p 개선); (2) 한자 판별
정확도를 +25.7%p 향상시킨 인접문장 공출현 임베딩 방법; (3) 음소 신뢰도, 문맥
유사도, 빈도, N-gram 점수를 결합하여 62.1% Top-1 표기 정확도를 달성한 4요소
랭킹 공식; (4) 학습량 스케일링, 어휘 확장, 윈도우 크기, 방향성 임베딩, 장음
분석 등 14개 차원에 걸친 포괄적 실험 평가; (5) KSPC 0.85의 macOS 및 Windows
네이티브 IME 구현.

#### 2. 시스템 구조

본 IME 시스템은 Rust 워크스페이스로 구현되어 있으며, core, hangul, japanese,
db, macos-ime, windows-ime, android-bridge, cli 등 8개의 크레이트로 구성된다.
변환 파이프라인은 입력되는 각 단어에 대해 4단계로 순차 실행된다.

**2.1 1단계: QWERTY → 한글 자모 조합**

물리적 키보드 이벤트(QWERTY 키코드)를 먼저 표준 두벌식 배치를 사용하여
한글 자모(자음과 모음)로 매핑한다. 자모는 유니코드 조합 공식(codepoint =
0xAC00 + cho×21×28 + jung×28 + jong)을 사용하여 한글 음절 블록으로
조합된다. 복합 모음(ㅗ+ㅡ→ㅘ)과 복합 자음(ㄱ+ㅅ→ㄳ)을 상태 머신으로 처리한다.

**2.2 2단계: 한글 → 히라가나 디코딩**

조합된 한글 문자열은 학습된 PhoneticMap과 BeamDecoder를 사용하여 히라가나
후보로 변환된다. PhoneticMap은 500K 학습 문장 쌍에서 학습된 통계 모델로,
각 한글 토큰을 확률 값이 부여된 하나 이상의 히라가나 시퀀스로 매핑한다.
BeamDecoder는 빔 폭 8, 최대 후보 20개로 빔 검색을 수행한다.

**2.3 3단계: 한자 후보 검색**

각 히라가나 후보는 한자 사전(KanjiDict)에서 가능한 모든 표기형을 검색한다.
예를 들어 히라가나 こうえん은 公園(공원), 講演(강연), 公演(공연), 後援(후원)
등의 후보로 매핑된다. 각 후보에는 학습 코퍼스에서의 빈도 정보가 포함된다.

**2.4 4단계: 문맥 인식 랭킹**

후보들은 4요소 가중 공식으로 점수화된다: `score = α·phoneme + β·context +
γ·frequency + δ·ngram` (α=0.1, β=0.35, γ=0.25, δ=0.3). 문맥 점수는 후보의
64차원 단어 임베딩과 이전에 확정된 단어들의 가중 평균 임베딩 간의 코사인
유사도로 계산된다. N-gram 점수는 바이그램/트라이그램 조건부 확률로 순차적
패턴을 포착한다.

#### 3. 실험 방법론

**3.1 코퍼스 생성**

모든 실험은 표기형, 읽기(히라가나), 한글 음역이 포함된 문장을 생성하는
합성 일본어 코퍼스 생성기를 사용한다. 생성기는 기본 어휘 1,442개 또는 확장
어휘 23,472개에서 2~5개 단어로 문법적으로 타당한 문장을 구성한다. 학습/테스트
세트는 인덱스 오프셋으로 분리하여 데이터 누출을 방지한다.

**3.2 평가 지표**

모든 실험에서 다음 지표를 사용한다: Top-1 표기 정확도(최상위 후보가 원본
표기형과 일치), 히라가나 Top-1(정답 읽기가 최상위 음소 디코드), 히라가나
Any-Hit(정답이 후보 목록 어디에든 포함), Top-K Hit Rate(K=3,5,10), 문서 전체
일치(문장 내 모든 단어 정확 변환), KSPC(물리적 키 입력 수 / 출력 문자 수).

**3.3 학습 구성**

별도 명시가 없는 한, 모든 실험은 다음 기본 구성을 사용한다: 학습 문장
500,000개, 64차원 단어 임베딩(SGD 50회 반복), 공출현 윈도우 크기 5, 테스트
문서 1,000건(계산 집약적 실험은 300건). 모든 벤치마크는 디스크 I/O 변동을
제거하기 위해 인메모리 SQLite 데이터베이스에서 실행한다.

#### 4. 실험 결과

**4.1 음소 디코딩: 규칙 기반 vs. 임베딩**

첫 번째 실험은 한글을 히라가나로 변환하는 두 가지 접근법을 비교한다: (A)
한글→로마지→히라가나 결정론적 규칙 파이프라인, (B) PhoneticMap + BeamDecoder
통계적 매핑. 양쪽 모두 동일한 문맥 랭킹을 사용한다.

| 지표 | 규칙 기반 (A) | 음소 임베딩 (B) | Δ (B−A) |
|---|---|---|---|
| 히라가나 Top-1 | 59.6% | 90.5% | +30.9%p |
| 히라가나 Any-Hit | 89.2% | 95.0% | +5.8%p |
| Top-1 표기 | 17.8% | 27.1% | +9.3%p |
| 읽기 일치 | 63.6% | 90.5% | +26.8%p |
| Top-10 Hit | 87.7% | 94.6% | +6.8%p |
| 문서 전체 일치 | 2.3% | 5.2% | +2.9%p |

*표 1. 음소 디코딩 비교: 규칙 기반 vs. 학습 임베딩 (500K 학습, 1000건 테스트)*

음소 임베딩 접근법은 히라가나 Top-1 정확도에서 +30.9%p의 극적인 개선을
달성하였다(59.6% → 90.5%). PhoneticMap은 224개의 고유 한글 토큰과 266개의
매핑을 학습하였으며(토큰당 평균 모호성 1.2개), 500K에서 10M 학습량까지
변화가 없어 음소 매핑 공간이 조기에 포화됨을 보여준다.

**4.2 마커 및 멀티토큰 음소 디코딩**

기본 음소 디코더에 대한 3가지 개선을 테스트하였다: (1) 모호한 음소 경계에
특수 기호를 삽입하는 마커 방식, (2) BeamDecoder가 단일 문자와 함께 2~3문자
한글 토큰을 고려하는 멀티토큰 방식, (3) 둘을 결합한 하이브리드. 멀티토큰
방식은 Top-10 상한을 94.5%에서 97.6%로 높였다(+3.1%p).

**4.3 인접문장 공출현 임베딩**

표준 단어 임베딩은 문장 내 공출현 패턴만 포착한다. 인접문장 공출현은
인접한 문장의 단어도 공출현 행렬에 기여하게 하여(cross_weight 가중치 적용)
더 넓은 주제적 일관성을 포착한다.

| 구성 | Top-1 표기 | 읽기 일치 | 문서 일치 |
|---|---|---|---|
| A. 기본 (문장 내 공출현만) | 26.5% | 90.5% | 4.7% |
| B. + 마커+멀티토큰 | 26.6% | 90.9% | 4.8% |
| C. + 인접문장 | 52.2% | 92.2% | 18.0% |
| D. + 모두 결합 | 53.8% | 92.2% | 18.0% |

*표 2. 조합 벤치마크: 마커+멀티토큰 × 인접문장 의미*

인접문장 문맥은 단일 최대 개선 요소로, Top-1 표기 정확도에 +25.7%p를
제공한다. 마커+멀티토큰 음소 개선은 인접문장과 결합 시 한계적 이익(+1.6%p)만
추가하여, 의미 판별 단계가 대부분의 음소 디코딩 오류를 이미 보상함을
시사한다.

**4.5 N-gram 언어 모델 통합**

랭킹 공식에 바이그램/트라이그램 조건부 확률을 추가하였다. N-gram 모델은

| 구성 | α | β | γ | δ | Top-1 표기 | Δ |
|---|---|---|---|---|---|---|

| δ=0.1 | 0.1 | 0.5 | 0.4 | 0.1 | 52.8% | +3.4%p |
| δ=0.2 (−β) | 0.1 | 0.3 | 0.4 | 0.2 | 55.5% | +6.1%p |

γ=0.25, δ=0.3)는 문맥 임베딩(β)과 빈도(γ) 모두에서 균등하게 가져왔으며,

**4.10 장음 마커 분석**

일본어 장음(예: こう /kou/, せい /sei/)은 한글 표현에서 상당한 모호성을
생성한다. 두 번째 모음(う 또는 い)이 별도 한글 문자로 매핑되기 때문이다.
한글 입력 스트림에 틸드(~) 마커를 삽입하여 장음을 명시적으로 표시하는
방법을 테스트하였다.

| 지표 | 기존 한글 | ~ 마커 적용 | 변화 |
|---|---|---|---|
| 히라가나 Hit | 96.3% | 74.0% | −22.3%p |
| Top-1 표기 | 61.6% | 48.7% | −12.8%p |
| Top-3 표기 | 85.2% | 66.2% | −19.1%p |
| 장음 단어 히라가나 Hit | 97.8% | 51.7% | −46.1%p |

*표 8. 장음 마커(~) 영향 분석 (300건 테스트, 최적 구성)*

장음 마커는 모든 지표에서 정확도를 급격히 저하시켰다. 히라가나 적중률이
22.3%p 하락했으며, 장음 포함 단어에서는 46.1%p의 치명적 하락을 보였다.
근본 원인은: (1) ~ 토큰이 PhoneticMap 학습 코퍼스에 부재, (2) 가타카나
장음 부호(ー) 변환 실패, (3) 추가 입력 부담이 이론적 모호성 해소 이익을
초과. 명시적 장음 마커 사용을 비추천하며, 문맥 기반 후처리를 권장한다.

> **연결 노트 (2026-07-25 업데이트, v0.1.7)**: 자동 변환이 여전히 장음을
> 놓치거나(아리가토 → ありがとう의 う 누락) 탁음을 잘못 고르는 경우가 있어,
> `KNOWN_WORDS`로 미리 등록해둔 단어가 아니면 여전히 발생합니다. 이번
> 버전에서 결국 사용자가 `~`/`^`를 직접 입력해 보정하는 기능을 붙였는데,
> **이 논문이 -22.3%p로 강하게 비추천한 바로 그 틸드 마커 방식입니다.**
> 그런데도 정확도 저하 없이 갈 수 있었던 이유는 이 논문의 실험과 아키텍처가
> 근본적으로 다르기 때문입니다:
>
> - 논문의 실험은 `~`를 **PhoneticMap 학습 코퍼스에 없는 새 토큰으로
>   입력 스트림에 섞어**, 문장 전체의 통계적 정렬을 어긋나게 만들었습니다
>   (원인 (1) "~ 토큰이 학습 코퍼스에 부재"). 즉 마커 하나가 문장 전체의
>   디코딩 품질을 떨어뜨렸습니다.
> - 반면 `decode_word_with_markers()`(1.6절)는 `~`/`^`가 붙은
>   **음절 하나에 한해서만** 별도의 결정적(deterministic) 경로로 빠지고,
>   문장의 나머지는 기존 `PhoneticMap`/`KNOWN_WORDS`/`KNOWN_SUFFIXES`
>   경로를 그대로 탑니다. 마커는 통계 모델에 "섞여 들어가는" 게 아니라
>   통계 모델을 "국소적으로 우회"할 뿐입니다 — 그래서 마커가 없는 나머지
>   문장의 정확도에는 영향이 없습니다 (`ime-db` 회귀 테스트로 고정됨).
>
> 즉 논문의 결론은 "**PhoneticMap을 학습시키는 코퍼스에 마커를 섞으면**
> 안 된다"는 뜻으로 좁혀 이해하는 게 맞고, "마커 기반 사용자 보정 자체가
> 나쁘다"는 뜻은 아니었습니다.

#### 6. 플랫폼 구현

**6.1 macOS (InputMethodKit)**

macOS 구현은 Apple의 InputMethodKit 프레임워크를 사용하며, Rust 코어
라이브러리를 정적 라이브러리(libhj_engine.a)로 컴파일하고 C FFI 레이어를
통해 Swift로 브릿징한다. TIS(Text Input Source) API로 시스템 입력 소스로
등록하고, IMKTextInput 프로토콜로 인라인 구성을 렌더링한다. 주요 구현
과제로는 Info.plist 구성, 설치 후 로그아웃/로그인 필요성, 메뉴 바 배지
아이콘(韓あ) 생성 등이 있었다.

**6.2 Windows (키보드 훅)**

Windows 구현은 WH_KEYBOARD_LL 저수준 키보드 훅으로 키 입력을 인터셉트하고,
KEYEVENTF_UNICODE 플래그의 SendInput으로 변환된 문자를 주입한다.
Ctrl+Space로 토글하며, 플랫폼 의존성 없이 순수 Rust로 한글 자모 조합을
구현하였다. 복잡한 TSF(Text Services Framework) 대신 키보드 훅 방식을
선택하여 구현 단순성과 Windows 10/11 호환성을 확보하였다.

#### 7. 논의

**7.1 주요 발견**

세 가지 발견이 돋보인다. 첫째, 음소 임베딩 단계가 빠르게 포화하여(224개
토큰, 500K~10M까지 불변), 한글-일본어 음소 매핑 공간이 본질적으로
제한적이며 병목이 전적으로 하류 한자 판별에 있음을 시사한다. 둘째,
인접문장 공출현 임베딩이 단일 최대 정확도 개선(+25.7%p)을 제공하여, 문장
경계를 넘는 주제적 일관성이 일본어 단어 예측에 강력한 신호임을 보여준다.
셋째, 비례적 학습 데이터 확장 없는 어휘 확장이 역효과적이라는 발견은
시스템 어휘 관리 전략에 직접적인 시사점을 준다.

**7.2 한계**

상용 IME와의 32.9%p 정확도 격차는 여전히 상당하다. 주요 한계는 확률적
히라가나 디코딩 단계로, 상용 IME는 결정론적 히라가나 입력을 받아 오류
원천 자체를 제거한다. 또한 합성 학습 코퍼스가 실제 일본어 텍스트의
복잡성을 완전히 포착하지 못할 수 있다. 명사 판별 병목(48.4%)은 범용
임베딩을 넘어서는 도메인 특화 솔루션이 필요하다.

**7.3 향후 연구**

상용 IME 수준으로 정확도를 향상시킬 수 있는 방향: (1) 실제 일본어 텍스트
코퍼스(예: 위키피디아, 뉴스 기사) 통합; (2) 명사 판별을 위한 의미 카테고리
제약 구현; (3) 문맥 랭킹을 위한 트랜스포머 기반 언어 모델 탐색; (4) 다음
단어 예측을 0.6%에서 사용 가능 수준으로 개선; (5) 확정된 선택으로부터
학습하는 사용자 적응.

#### 8. 결론

본 논문은 Top-1 표기 정확도 62.1%, KSPC 0.85를 달성한 완전한
한글→일본어 입력기 엔진을 제시하였다. 14개의 체계적 실험을 통해 크로스
링귀스틱 IME 정확도의 핵심 요소를 식별하였다: 음소 임베딩 품질, 문장 간
의미 문맥, N-gram 언어 모델링, 적절한 어휘-학습데이터 비율. 인접문장
공출현 임베딩이 단독으로 +25.7%p를 기여하여 가장 영향력 있는 아키텍처
혁신이었다. 본 시스템은 한글 음소 인코딩이 기존 로마지보다 근본적으로 더
효율적인 일본어 입력 매체임을 입증하였으며, 문자당 키 입력을 57.5%
절감하면서 사용 가능한 변환 정확도를 유지한다. macOS 및 Windows 네이티브
구현으로 실용적 배포 가능성을 확인하였다.

## 6. + 알파 — 이 논문과 실제 배포 앱의 관계

논문 전문을 그대로 옮겨두긴 했지만, **1~4절에서 설명한 실제 배포 중인
macOS 앱(v0.1.3)은 이 논문이 설명하는 시스템과 완전히 같지 않습니다.**
헷갈리지 않도록 정확한 관계를 정리합니다.

### 6.1 무엇이 겹치고 무엇이 안 겹치는가

| 논문이 설명하는 구성 요소 | 코드 위치 | 실제 앱 라이브 타이핑 경로(`hj_hangul_to_hiragana`)에 연결됨? |
|---|---|---|
| PhoneticMap + BeamDecoder (한글→히라가나) | `phonetic_decoder.rs` | ✅ 예 — 다만 4장 실험은 **합성 코퍼스 500K 문장** 기준, 실제 앱은 **검증된 어휘 4,153개**(1.4절 규모와 다름) |
| 음소 임베딩(64차원 단어 벡터) | `embedding.rs` | ❌ 아니오 — 조사/활용형 예외 규칙(1.5절)으로 대체됨 |
| 인접문장 공출현 임베딩 | `sentence.rs` (`SentenceBuffer`) | ❌ 아니오 — 라이브 타이핑은 단어 단위 처리, 문장 간 문맥 참조 없음 |
| N-gram 언어 모델 | `ngram.rs` | ❌ 아니오 |
| 한자 판별(KanjiDict + ContextRanker) | `dictionary.rs` | ⚠️ 부분적 — `hj_convert()`(후보창용)만 사용, 기본 조합 텍스트 경로(`hj_hangul_to_hiragana`)는 히라가나까지만 감 |
| 자동 완성 | `autocomplete.rs` | ❌ 미배선 (CLI 벤치마크에만 존재) |

즉, **논문은 "만약 한자 판별까지 하는 풀 파이프라인을 붙이면 어떻게 될까"를
실험한 연구 기록**이고, 실제 배포된 v0.1.3은 그중 **히라가나 변환 단계만
떼어내어 제품화**한 것입니다. 한자 후보/문맥 랭킹/N-gram은 코드로는
존재하지만 사용자가 타이핑할 때 실제로 호출되는 경로에는 없습니다.

### 6.2 정확도 수치를 그대로 믿으면 안 되는 이유

- 논문의 62.1%/90.5% 등은 **합성 생성 코퍼스**(실제 사람 문장이 아니라
  `generator.rs` 템플릿으로 만든 문장) 기준입니다. 4.7절 스스로도 밝히듯
  이런 수치는 어휘·학습량 비율에 민감합니다.
- 반면 이 문서 4.5절 "알려진 한계"와 세션 중 실제로 검증한 사례(`아나타노
  나마에와 난데스카`, `곤니찌와` 등, `phonetic_decoder.rs`의
  `test_wa_particle_is_ha_standalone_and_attached` 등 회귀 테스트로 고정됨)는
  **실제 프로덕션 코드 경로(검증된 어휘 4,153개 + BeamDecoder)를 사람이 손으로 만든
  실제 문장에 직접 돌려서 발견한 결과**입니다. 두 수치 체계는 같은 잣대가
  아니므로 직접 비교하지 마세요.

### 6.3 이 논문에서 아직 살리지 않은 아이디어 (향후 개선 후보)

- **인접문장 공출현 임베딩**(+25.7%p, 논문에서 가장 큰 단일 개선 요인)을
  실제 라이브 타이핑 경로에 연결하면, `KNOWN_WORDS`/`KNOWN_SUFFIXES`
  같은 고정 규칙 없이도 조사·문맥 오류 상당수가 통계적으로 해소될 가능성.
  다만 `SentenceBuffer`가 실제 IME 입력 흐름(글자 단위로 즉시 커밋되는
  구조)과 맞물리게 재설계가 필요함.
- **N-gram 모델**(+6.7%p) — 짧은 문구 위주인 지금 예외 규칙 방식보다
  일반화가 잘 될 가능성.
- 논문 7.3절이 제안한 "실제 일본어 텍스트 코퍼스(위키피디아 등) 통합"은
  1.4절에서 확인했듯 **한 번도 실제로 완료된 적이 없습니다** —
  `data/hj-ime-large.db`는 시도의 흔적만 남은 빈 파일이었습니다. 이번에
  다시 시도한다면, 크롤링한 원문을 저장소에 커밋하지 말고(용량 문제)
  빌드 시점에 외부에서 내려받는 파이프라인으로 설계하는 게 안전합니다.
